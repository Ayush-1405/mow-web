## Exact changes, by correction number

**1. `staff_create_task` — from-department validation (new).** Previously any active user could set `p_from_department_id` to anything active. Now: employee/supervisor must pass their own `department_id`; Department Head must pass a department inside `staff_dept_in_hod_scope()`; Management is unrestricted but still blocked by the existing confidential-department check; any other role (including `sysadmin`) is rejected outright. Also added: `from_department_id` itself can never be a confidential department, for anyone — see the flagged interpretation note below.

**2. `staff_create_task` — assignee/verifier department validation (new).** `p_assigned_to` must now match `p_to_department_id` exactly (not merely "active"). Verifier authorization is now checked against the destination department using two new helper functions, `staff_user_role_code(uuid)` and `staff_user_dept_in_hod_scope(uuid, uuid)` — parameterized versions of the existing caller-only helpers, needed because the verifier/assignee being validated is not `auth.uid()`.

**3. `staff_directory` view removed, replaced by `staff_list_assignable_users(p_department_id)`.** The v2 view was `SECURITY INVOKER`, which meant it ran under `user_profiles`' own RLS — an ordinary employee's dropdown query would have returned only their own row. The replacement is a `SECURITY DEFINER` RPC with its own visibility logic (own department for employees, plus any other non-confidential department for Bridge-recipient lookup; own scope for HOD; Accounts-only for Accounts Head; unrestricted for Management), returning only the 6 approved columns. `DROP VIEW IF EXISTS public.staff_directory;` is included defensively even though it was never deployed.

**4. `user_location_access_select_scoped` — role-gated.** v2's version called `staff_dept_in_hod_scope()` directly with no check that the caller was actually a Department Head, which would have let an ordinary employee see a same-department colleague's location-access rows. v2.1 requires `staff_is_management()` OR (`staff_is_accounts_head()` AND target user is in Accounts) OR (`staff_is_dept_head()` AND target user's department is in that Head's scope).

**5. `staff_return_task` — ASSIGNED-stage actor fixed.** v2 checked `current_owner_id = auth.uid()` uniformly across ASSIGNED/ACCEPTED/IN_PROGRESS. That's wrong at ASSIGNED: `current_owner_id` is still the *sender* at that point (sender remains owner until acceptance), so v2 would have let the sender "return" their own just-created task instead of letting the intended receiver decline it. v2.1 branches explicitly: ASSIGNED → actor must be `assigned_to`; ACCEPTED/IN_PROGRESS → actor must be `current_owner_id`; COMPLETED → verifier/HOD/Management, unchanged.

**6. Explicit status preconditions added to every action RPC.** `staff_accept_task` now requires `ASSIGNED` or `RETURNED`; `staff_start_task` requires `ACCEPTED`; `staff_complete_task` requires `IN_PROGRESS`; `staff_verify_task` requires `COMPLETED`; `staff_close_task` requires `VERIFIED`; `staff_reassign_task` and `staff_request_help` both reject `CLOSED`. Because each check `RAISE EXCEPTION`s before any `UPDATE`/audit/notification statement runs, a repeated call aborts the whole function (single transaction) with no partial side effects — so no duplicate audit rows or duplicate notifications can occur from a double-click or a replayed request.

**7. `staff_reassign_task` — rewritten.** `p_reason` is now a required parameter (function signature changed: `(p_task_id, p_reason, p_new_assigned_to DEFAULT NULL, p_new_verifier_id DEFAULT NULL)`), rejected if blank. New assignee's `department_id` must exactly match `to_department_id`. Blocked entirely on `CLOSED`. Ownership transfer is stage-aware: before acceptance (ASSIGNED/RETURNED) only `assigned_to` changes, since the sender still owns the task; once ACCEPTED/IN_PROGRESS, `current_owner_id` moves to the new assignee too. `bridges.to_person_id` is updated in the same function call when the task `is_bridge`. Both the old and new assignee get a notification. The reason is written into `staff_audit_log.remarks` as well as the JSON payload.

**8a. `staff_record_attachment` — storage-object verification (new).** Before inserting metadata, the function now looks up `storage.objects` for `bucket_id = 'staff-attachments' AND name = p_storage_path`. If no row exists, it refuses ("orphan/fake metadata" is rejected outright). Where Storage recorded its own `size`/`mimetype` in `metadata`, those values are checked against the client-supplied `p_file_size`/`p_mime_type` and any mismatch is rejected — so a filename extension or a claimed MIME type alone can no longer satisfy proof requirements; what Storage itself recorded at upload time is the source of truth.

**8b. Drawing MIME whitelist (new).** `file_type = 'drawing'` now requires `mime_type` in an explicit list (`application/dxf`, `application/dwg`, `image/vnd.dwg`, `image/vnd.dxf`, `application/x-dwg`, `application/x-dxf`, `application/acad`). **Flagged for your review**: this list is a reasonable starting set for common CAD export formats, not a verified match to whatever tool your drawing files actually come from — narrow or extend it before go-live.

**8c. `upload_url` Edge Function — spec updated (not deployed, no SQL).** Documented requirement, not code: the function must validate the caller's access to the parent task/Bridge (same rule as `staff_attachments_select_matches_parent`) *before* minting a signed upload URL, and the client must call `staff_record_attachment` immediately after upload so the new storage.objects check (8a) can catch anything that didn't actually get written to the bucket.

**9. Execution-privilege audit (new, consolidated section 19 of the migration file).** Every function got an explicit `REVOKE ALL ... FROM PUBLIC, anon` (and `authenticated` for the internal-only ones), followed by an explicit `GRANT EXECUTE` to exactly the role that needs it. This surfaced a real gap in v2: the RLS-support helper functions (`staff_current_user_ok`, `staff_current_role_code`, `staff_is_management`, `staff_is_dept_head`, `staff_is_accounts_head`, `staff_current_department_id`, `staff_current_department_group_id`, `staff_dept_in_hod_scope`) were never explicitly granted `EXECUTE` to `authenticated` in v2 — they happened to work only because Postgres grants `EXECUTE` to `PUBLIC` by default on function creation, which v2 never revoked for them. v2.1 makes this explicit rather than accidental: revoke from `PUBLIC`/`anon`, grant to `authenticated` by name.

## Flagged assumption carried into v2.1 (please confirm)

Item 1's instruction ("Management may use any active **non-confidential** operational department") is applied literally and **uniformly to every role**, not just Management — nobody, including Management, can set `p_from_department_id` to a confidential department in this pilot. Practical effect: **Accounts/Finance staff cannot create any task through `staff_create_task` at all right now**, even a same-department Accounts-internal task, since their own department is the confidential one. This is consistent with your original instruction to disable Accounts cross-department workflows rather than half-implement a safe summary (item 18 from the prior round), extended here to same-department Accounts tasks too, since the correction text didn't carve out an exception for same-department. If you want Accounts-internal (same-department, non-Bridge) task creation to work in this pilot, tell me and I'll narrow the check to only block when `from_department_id <> to_department_id` and either side is confidential — i.e., restore same-department Accounts task creation while keeping cross-department Bridges into Accounts blocked.

Also flagged: `staff_list_assignable_users` has a gap for `accounts_employee`/`cfo` callers browsing their *own* (confidential) department's directory — they fall into the generic "employee" branch, which refuses confidential targets. Accounts-internal directory needs are expected to route through the Accounts Head for this pilot; tell me if `accounts_employee`/`cfo` need their own directory access to teammates.

## Tests (Correction 10)

Each of these should run against `mvp_pilot_migration_v2_1.sql` + `mvp_pilot_rls_policies_v2_1.sql` once approved and applied to a non-production branch/project — none have been run yet.

1. **Spoofed from-department**: as an Employee in Retail, call `staff_create_task` with `p_from_department_id` = Factory's id → expect rejection ("You may only create tasks from your own department").
2. **Cross-department assignee mismatch**: call `staff_create_task` with `p_to_department_id` = Factory but `p_assigned_to` = a user whose `department_id` is Godown → expect rejection.
3. **Directory dropdown correctness**: as a plain Employee, call `staff_list_assignable_users()` with no argument → expect only active users in the caller's own department, with exactly the 6 approved columns (assert `phone`, `joining_date`, `reports_to` are absent from the result shape). Then call it with a different active non-confidential department id → expect that department's active users returned (Bridge-recipient lookup case). Then call it with a confidential department id → expect rejection.
4. **Location-access privacy**: as a plain Employee, query `user_location_access` for a colleague's `user_id` → expect zero rows (only `user_location_access_select_own` applies to them).
5. **Unaccepted task can be declined**: `staff_create_task` a task assigned to User B; before B accepts, call `staff_return_task` as B with a reason → expect success and `current_owner_id` unchanged from B's perspective of visibility (still the sender, per the ownership rule) but status = RETURNED. Also confirm the *sender* attempting the same call is rejected (only the receiver may decline at ASSIGNED).
6. **No duplicate side effects on repeat calls**: call `staff_accept_task` twice in a row for the same task → first succeeds, second fails with a precondition error; assert `staff_audit_log` has exactly one `ACCEPT` row and `notifications` has exactly one row from that action. Repeat the same pattern for `staff_complete_task` and `staff_verify_task`.
7. **Bridge reassignment sync**: create a cross-department task/Bridge, then call `staff_reassign_task` with a `p_new_assigned_to` in the same destination department → assert both `staff_tasks.assigned_to` and `bridges.to_person_id` reflect the new person in the same check, and both the old and new assignee received a notification.
8. **Fake attachment metadata rejected**: call `staff_record_attachment` with a `storage_path` that was never actually uploaded to the `staff-attachments` bucket → expect rejection ("No uploaded object found..."). Separately, upload a real object but call `staff_record_attachment` with a `p_file_size` that doesn't match the object's actual recorded size → expect rejection.

Plus, carried over from v2's test plan (still applicable, not re-listed in full here): zero direct-write policies on the five RPC-gated tables, the full Accept→Close lifecycle via correct actors, wrong-actor rejection at each stage, active/must-change-password enforcement mid-session, Interior-dashboard tables unchanged, and the "unique and concurrency-safe, gaps allowed" task/Bridge number wording.
